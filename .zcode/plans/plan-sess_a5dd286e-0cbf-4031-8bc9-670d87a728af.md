# MiniMapStatus → 独立LLM驱动的轻量状态管理系统（修订版）

## 核心结论（回答你的三个原始疑问）

1. **"系统深度0注入聊天记录"** —— 不写入聊天记录。用酒馆助手原生 `injectPrompts({position:'in_chat', depth:0, role:'system', content: 完整状态栏YAML})`：语义上完全等于"系统身份、深度0"，但不产生楼层、不污染阅读流、不占输出token。**注入内容 = 完整状态栏YAML，仅剔除「行动选项」小节**（正文API需要知道全部当前状态来写剧情，行动选项推荐只给人看不进提示词）。注入随聊天切换/页面刷新由渲染器自动重挂（幂等：固定id，先uninject再inject）。
2. **"LLM更新可以实时刷新吗"** —— 可以。更新器完成后 `eventEmit('mms:updated')`，楼层末尾的iframe收到事件后**原地重渲染自己的DOM**（重读本楼变量→更新卡片/地图），不重载iframe、不动其他楼层、不打断阅读/生图/音效。
3. **"能兼容当前YAML格式吗"** —— 能。独立LLM用 `json_schema` 强制输出**与现有YAML schema一一对应的JSON**（量化字段如HP/MP/SAN/坐标加`pattern`校验，内心/穿着/描述等为自由字符串，不校验），程序 `jsyaml.dump` 转成同样格式的YAML。现有 StoryRenderer、立绘引擎、战术地图、六主题、设置面板**全部保留，几乎零改动**——变的只是数据从哪来。

## 痛点 → 解法

| 痛点 | 解法 |
|---|---|
| 正文API写正文时还要考虑输出状态栏 → 楼层慢、生图/音效插件延迟 | 正文API只输出正文+IMG_GEN+**末尾一个约10 token的标记 `【状态栏标记点】`**（参考MVU占位符思路）。楼层完成大幅提前 |
| 正文API对状态栏的注意力消耗 | 正文提示词中不再有大段Status_block schema输出指令；当前状态经深度0注入回喂（见上），正文与数值保持一致 |

## 目标架构（单工件，部署方式与现在完全相同）

**唯一交付物仍是那份HTML**（渲染器+管理器一体），经局部正则替换为酒馆助手iframe——PC/手机同一通道（你确认的使用方式；实测手机专用旧正则已禁用，生效的是局部正则「美化状态栏[立绘性能优化]」）。

```
正文API输出: <maintext>正文</maintext> + [IMG_GEN]…[/IMG_GEN] + 【状态栏标记点】
                ↓ (楼层渲染完成，正则把标记替换为iframe，即刻可见)
iframe渲染器(每楼):
  ├ 读本楼消息变量 stat_data → 无则显示上一楼状态+"⏳更新中"骨架
  ├ 若本楼是最新楼 且 stat_data缺失/文本哈希不匹配 → 自动触发更新
  ├ 更新引擎: generateRaw/generate + custom_api(独立端点/密钥/模型)
  │   + json_schema(完整状态结构, 量化字段pattern校验, 自由字段为纯string)
  │   输入: 当前状态YAML + 最近楼层maintext + 更新指令
  │   输出: 完整状态JSON(全量协议,第一步) → 校验/夹取(坐标0-1000等)
  │   → insertOrAssignVariables({stat_data}, {type:'message', message_id:本楼})
  ├ 注入引擎: injectPrompts 深度0 system = 最新状态YAML(去除行动选项, 每次更新后刷新)
  └ eventEmit('mms:updated') → 本楼iframe原地刷新状态栏
```

关键设计点：
- **每楼每swipe独立快照**：状态存楼层变量（swipe安全、随聊天导出、旧楼层显示当时状态）；用消息文本哈希（存`$mms_meta`，`$`前缀宏对AI不可见）检测swipe/编辑后自动重更新。
- **并发防护**：`initializeGlobal/waitGlobalInitialized` 跨iframe更新锁；新楼层触发时取消旧楼层未完成的更新（`stopGenerationById`）。
- **失败策略**：重试2次（1s/2s退避）；失败保留旧状态+红色角标+手动重试按钮。json_schema不支持的自定义端点降级链：json_schema → response_format json_object → 提示词强制+JSON.parse修复。
- **标记漂移兜底**：更新器检测到楼层末尾无标记时用 `setChatMessages` 补写（罕见场景才触发一次单楼重渲染）。
- **配置存储**：独立API配置（端点/密钥/模型）存酒馆助手**全局变量**（绑定用户存档，PC/手机共用）；数据存聊天/楼层变量。

## 风险与对策
- **iframe生命周期**：更新由"最新楼iframe渲染时自触发"，无需常驻全局脚本（部署保持单工件）；楼层被滚动卸载等边缘场景由手动更新按钮兜底
- **与ACU共存**：ACU的世界书条目注入与我们的深度0注入并存不冲突（不同深度/顺序），M2再做数据层面协调
- **事件跨iframe**：eventEmit/eventOn为酒馆助手官方跨iframe机制（MVU同款），实现时验证，失败则降级为直接查询父页面iframe DOM调用其暴露的刷新函数
- **json_schema依赖端点能力**：主流源均支持，已列降级链
