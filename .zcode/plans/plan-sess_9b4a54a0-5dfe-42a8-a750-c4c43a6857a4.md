# MiniMapStatus 性能优化计划（运行时性能 + 源码体积）

## 诊断结论

849KB / 16773 行，问题按影响排序：
1. **Tailwind CDN 运行时编译器**（`cdn.tailwindcss.com`，266 行）：~110KB 每楼下载；与 innerHTML 全量重绘叠加，每次重绘触发 Tailwind 重扫描重编译（可见 10 楼 × 每次刷新的持续 CPU 税）。而 2200 行 `text/tailwindcss` 块实测零 @apply、全是原生 CSS，根本不需要 Tailwind。
2. **渲染链路 YAML dump→load 往返**：`renderFromState`（~12520）每次刷新都 `stateToYaml` 写 script 标签 → `reRenderStatusBar`（9390）→ `jsyaml.load` 解析回来，纯冗余。
3. **立绘引擎**（7–258 行）：MutationObserver 永不 disconnect，渲染期 DOM 变化反复触发 `querySelectorAll("div, li, section")` 全扫 + `document.body.innerText` 全读（强制 reflow）。
4. **SVG 场景模板 182KB（占 31%）**：含确认不可达的 `nightmarket` 死分支；场景名匹配链（5244–5306）宽泛词（广场/中心/公园/庭院）前置遮蔽具体场景（夜市/修仙系），部分 case 难以命中（半死）；grass pattern 重复 2 份、wood/carpet/floor 等成对变体各 case 重复实现。
5. **主题 CSS 五套复制**：day/jade/classic/romantic/five 成套选择器（386–650、860–2500+ 两批）。

部署层不动（优化插件已控制可见楼层数，保持每楼渲染）。

## 实施步骤（每步完成即 git 提交一次）

### 第 1 步：Tailwind 构建期编译内联，删 CDN（运行时最大项）
- 扩展 `build_regex.mjs`（或新建 `build_tailwind.mjs` 被其调用）：
  1. 从源 HTML 提取内联 `tailwind.config`（269–339 行）生成临时 config 文件；
  2. `npx -y tailwindcss@3` CLI 以 MiniMapStatus.html **全文**为 content 扫描生成工具类 CSS（静态 HTML + JS 模板字符串类名全覆盖；已确认动态拼接类名仅 `env-${envType}` 一处且是自定义 CSS 类，非工具类，不受影响）；
  3. 产物 CSS 写回源 HTML 的标记区块（`<!-- TAILWIND BUILD OUTPUT START/END -->`），同时删除 `<script src="https://cdn.tailwindcss.com">`、`tailwind.config` script 块。
- `text/tailwindcss` style 块（340–2548）改成普通 `<style>`，内容一字不动（`@layer utilities` 是标准 CSS，浏览器原生解析）。
- 工作流变化：改类名/主题色后需跑一次构建刷新产物区块（原本改完也要跑 build 生成正则 JSON，不增加负担）。
- 验证：构建前后 IAB 截图对比五套主题 + 主要面板（角色卡/地图/设置面板/灯箱），确认零样式丢失。

### 第 2 步：渲染链路去掉 YAML dump→load 往返
- `renderFromState` 不再 `updateYamlDataSource(stateToYaml(...))` + `reRenderStatusBar` 经 script 标签往返，改为直接把 state（display 副本）传给 StoryRenderer 渲染。
- 保留 `yaml-data-source` 作为本地打开预览的初始数据入口（仅首读一次）。
- 梳理 `reRenderStatusBar` 全部调用点统一走直通路径。
- 验证：harness（integration-test/harness.html）全绿 + IAB mock 冒烟（AI 更新/表单编辑/事件刷新/页签切换）。

### 第 3 步：立绘引擎扫描修复（小改动）
- `attemptCount` 达 MAX_ATTEMPTS 后 `observer.disconnect()`。
- 扫描先 `querySelectorAll` 立绘标签命中再读文本，去掉 `document.body.innerText` 全读。
- 验证：IAB 确认立绘注入与灯箱切换正常。

### 第 4 步：SVG 死分支删除 + 场景匹配顺序修复（体积+正确性）
- 删不可达 `case 'nightmarket'`（6515–6544）。
- 重排构造器匹配链（5244–5306）：具体场景关键词提到宽泛词之前；整理完整"关键词→场景"映射表，对照 45 个 case 逐一核对可达性。
- 注意：部分楼层的地图会变为更准确的场景（有意修正，显示会变）。
- 验证：临时测试页枚举全部场景关键词渲染，改动前后截图人工比对。

### 第 5 步：SVG 公共 pattern 去重（体积）
- 把 grass/wood-floor/wood-lines/carpet-b/carpet-d/floor-b/floor-d/tile/asphalt 等跨 case 重复的 pattern 抽成共享生成函数（保留 `${uid}` 注入保证 id 唯一），各 case 模板引用。
- 只做确定性高的通用 pattern，不做 45 个 case 全量重构。
- 验证：同第 4 步场景截图比对。

### 第 6 步（可选，视前 5 步后的收益决定）：主题 CSS 变量化
- 五套 mode 选择器提成 CSS 变量 + 单份选择器，预计再省几十 KB，但改动面大（五套主题 × 全部组件的视觉回归）。默认本次不做，落地前 5 步后按实际效果再议。

## 收尾
- 全部步骤完成后：`node --check` 校验主脚本 → harness 全绿 → IAB 最终冒烟 → `node build_regex.mjs` 重建两个正则 JSON → 报告等待用户导入酒馆实测（不代替导入）。
- 每步一次 git 提交，会话末尾汇总短 hash。

## 预期效果
- 每楼 iframe：省 ~110KB CDN 下载 + 消除持续 JIT 编译税；每次状态刷新省一次 YAML dump/load 往返；立绘扫描不再全 DOM 反复扫。
- 源文件：SVG/死码预计减 30–60KB（Tailwind 产物内联约 +40–60KB 部分对冲，运行时净收益显著为正）。

## 备注（不在本次范围，仅提示）
若目标是"酒馆里加载的字节数变小"，构建期 minify（源码保持可读、产物自动 -20~30%）是收益/风险比最高的一项，本次按你的选择未纳入；后续可随时单独加。js-yaml 与 font-awesome CDN 保持现状（有 HTTP 缓存共享，收益小）。
